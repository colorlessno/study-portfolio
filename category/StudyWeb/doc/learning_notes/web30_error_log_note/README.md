# web30 エラーを再利用できる知識として残す

発生したエラーを貼るだけで終わらせず、再現条件、仮説、確認、原因、解決、次回の切り分け方法として記録するテーマです。

## このテーマでできるようになること

- エラーメッセージと発生条件を再現可能な形で残せる
- 原因の仮説と確認済みの原因を区別できる
- Console、Network、ログ、設定のどこを見たか記録できる
- 同じ問題を検索しやすいタグと次回確認ポイントを付けられる

## 資料を見る前の確認問題

- エラーメッセージだけを残しても再現できないのはなぜですか。
- 「たぶんCORS」と「Response Headerを確認してCORSと判断した」は何が違いますか。
- 解決後に次回確認ポイントを残す利点は何ですか。

## 15分で再開する

1. 2つの記入例を比較する。
2. 最近見たエラーを1件選ぶ。
3. テンプレートへ環境、再現手順、エラー原文を書く。
4. 原因を断定せず、確認した証拠を1つ追加する。

## 記録の流れ

```text
現象を保存
  ↓
最小の再現手順を作る
  ↓
仮説を立てる
  ↓
Console / Network / logs / diffで確認
  ↓
原因と解決方法を分けて書く
  ↓
再発時の最初の確認箇所を残す
```

## 書き分ける内容

| 項目 | 書く内容 |
|---|---|
| エラー内容 | 改変していない主要メッセージとstatus |
| 再現手順 | 別の人が同じ現象を出せる操作 |
| 原因 | 証拠から確定した理由 |
| 解決方法 | 実際に行い、直ったことを確認した変更 |
| 次回確認 | 同じ症状で最初に見る場所 |

## 演習

1. web03でCSSパスを一時的に壊し、Networkの失敗をテンプレートへ記録する。
2. web21で存在しないAPIパスを呼び、404とnetwork errorを区別して記録する。
3. 原因を先に書かず、観察事実だけから仮説を2つ作る。
4. 修正後に同じ再現手順を実行し、解決確認を追記する。

## 自分の言葉で説明する

- 現象、仮説、原因、対処の違いを説明してください。
- エラー記録に環境と関連ファイルが必要な理由は何ですか。
- 良いエラーログを将来のStudy Hubでどう検索したいですか。

## 記録時の注意

- APIキー、パスワード、Cookie、個人情報、実在の接続文字列を貼らない。
- 長いログを全部貼らず、原因調査に必要な箇所と取得方法を残す。
- 解決していない場合は「未解決」と明記し、推測を事実として書かない。
- 画面キャプチャだけに依存せず、検索可能なテキストも残す。
