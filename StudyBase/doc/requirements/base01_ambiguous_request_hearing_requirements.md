# base01 曖昧依頼ヒアリング 要件定義

## 1. 目的

曖昧な依頼を受けたときに、目的、現状、課題、制約、成功条件、未確定事項へ分解できるようにする。

「何か改善して」「売上を上げて」「取りこぼしをなくして」のような依頼を、すぐ実装案へ飛ばさず、仕事として扱える形に変換する。

## 2. 学習対象

- 要求定義と要件定義の違い
- ヒアリング項目の作り方
- 目的、現状、課題、制約、関係者、成功条件の分離
- 未確定事項と確認事項の管理
- AI に要件定義を依頼する前の入力整理

## 3. 作成する成果物

- ヒアリングメモテンプレート
- 曖昧依頼のサンプルケース
- ヒアリング後の整理例
- 未確定事項一覧
- 要件定義へ渡すための要約メモ

## 4. 機能要件

| ID | 要件 |
|---|---|
| FR-01 | 曖昧な依頼文を入力例として用意できる |
| FR-02 | 依頼を目的、現状、課題、制約、関係者、成功条件へ分解できる |
| FR-03 | 確定情報、仮定、未確定事項を分けて記録できる |
| FR-04 | 確認すべき相手、確認内容、期限を記録できる |
| FR-05 | 要件定義へ渡す要約メモを作成できる |

## 5. 非機能要件

| ID | 要件 |
|---|---|
| NFR-01 | テンプレートは Markdown で読み書きできる |
| NFR-02 | 特定業務に依存しすぎず、Web / AI / 運用改善で使い回せる |
| NFR-03 | 情報不足を無理に埋めず、未確定事項として残せる |

## 6. 対象外

- 実システムの要件定義完成版を作ること
- 見積もり作成
- UIやAPIの設計
- 実装

## 7. 受入条件

- 曖昧依頼を、目的、現状、課題、制約、成功条件へ分解できる
- 未確定事項と確認事項が別管理されている
- 要件定義へ渡せる入力メモが作成できる
- 「分からないことを分からないまま残す」形式になっている

## 8. 学習観点

- 依頼文からすぐ仕様を作らない
- 確定情報、仮定、未確定事項を混ぜない
- AI に丸投げする前に入力条件を整える
