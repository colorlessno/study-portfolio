# web29 学習用READMEの書き方

READMEを起動コマンドの置き場だけにせず、学習目的、観察方法、故障演習、説明課題、完了条件まで含む「再開地点」として設計するテーマです。

## このテーマでできるようになること

- 初見の人が目的と起動方法を判断できるREADMEを書ける
- 実行した事実と未確認事項を区別して記録できる
- 設計、実装、確認手順をリンクで接続できる
- 秘密情報を含めずに設定方法を説明できる

## 資料を見る前の確認問題

- READMEの読者は、最初の1分で何を判断したいでしょうか。
- 「動くはず」と「実際に確認した」を同じ書き方にすると何が困りますか。
- 起動方法だけでは、時間が空いた後に何が不足しますか。

## 15分で再開する

1. [記入例](../../templates/web29_readme_template/README.example.md)を読む。
2. 自分が最近触ったテーマを1件選ぶ。
3. 「目的」「最短実行」「観察ポイント」を各1項目だけ書く。
4. 書いた手順を上から実行し、不足を1つ修正する。

## READMEの推奨構成

| セクション | 読者が判断できること |
|---|---|
| 概要・到達目標 | 何を学ぶテーマか |
| 前提 | 今の環境と知識で開始できるか |
| 関連資料 | 要件・設計・実装をどこから辿るか |
| 最短実行 | 最小手順で再現できるか |
| 確認する流れ | 何を観察すれば成功か |
| コードを読む順番 | どこから読めば処理がつながるか |
| 壊して直す演習 | 原因調査を経験できるか |
| 自分の言葉で説明する | 理解を思い出せるか |
| 完了条件 | どこまでできれば次へ進めるか |

## 作成手順

1. テーマ名と学習目的を1〜2文で書く。
2. 要件、基本設計、詳細設計、実装への相対リンクを置く。
3. 作業ディレクトリを明記して起動コマンドを書く。
4. URL、API、DB、Network等の確認先を書く。
5. 正常系と少なくとも1つの異常系を書く。
6. 実際に手順を実行し、確認した結果だけを完了扱いにする。

## 壊して直す演習

1. 作業ディレクトリを書かない手順を別の場所から実行し、曖昧さを確認する。
2. 確認URLを1文字誤らせ、読者が修正できる情報があるかを見る。
3. 「確認済み」と「未確認」を分けずに書き、誤解が生じる箇所を探す。
4. 既存READMEを別PC・別シェルの読者として読み、暗黙の前提を3つ探す。

## 自分の言葉で説明する

- 良いREADMEが学習の再開時間を短くする理由は何ですか。
- 起動方法と確認方法を分ける理由は何ですか。
- ポートフォリオ向け説明と学習者向け説明の共通点・相違点は何ですか。

## 秘密情報と事実性

- APIキー、パスワード、個人情報、実在の接続文字列を書かない。
- `.env.example`にはダミー値だけを置く。
- 実行していないテストを成功済みと書かない。
- 環境依存の手順にはOS、シェル、前提ツールを明記する。

## 学習完了の目安

- [ ] 既存テーマ1件のREADMEを推奨構成で書いた
- [ ] 別の場所から最短実行を再現した
- [ ] 正常系と異常系を1件ずつ確認した
- [ ] 秘密情報と未確認事項が含まれていないことを見直した
