# system48 基本設計

## ローカルLLMによるAI組織運用

## 0. 関連要件

- `../requirements/system48_local_llm_agent_organization_requirements.md`

## 1. 設計目的

ローカルLLMを使った複数のAIエージェントを役割ごとに分け、タスクボード・共有記憶・判断ログ・レビュー結果を通じて非同期に連携するAI組織運用を学ぶ教材にする。

この基本設計では、AIに全ての情報を渡す構造ではなく、役割ごとに必要な情報だけを渡し、危険操作は人間確認に止める構造を定義する。

## 2. 対象領域

- AI組織のロール定義
- ロールごとの入力文脈の分離
- タスクボードによる非同期連携
- 共有記憶と判断ログ
- レビュー・QA・安全確認の流れ
- ローカルLLM呼び出しと模擬実行の切り替え
- 人間確認を挟む承認基準
- 実行ログと停止条件

## 4. 基本構造

```text
利用者
  ↓ タスクボード
  ↓ 調整役
  ├─ 計画担当
  ├─ 設計担当
  ├─ 実行案担当
  ├─ レビュー担当
  ├─ QA担当
  ├─ 記録担当
  └─ 安全確認担当
  ↓ 判断ログ / 共有記憶 / レビュー結果
  ↓ 最終報告
```

各担当は直接会話しない。前の担当が残した成果物を読み、次の成果物をファイルに残す。調整役は、タスクの状態・未解決事項・人間確認が必要な項目を整理する。

## 5. ロール設計

| ロール | 主な責任 | 主な成果物 |
|---|---|---|
| 調整役 | タスクの分割・担当決定・停止条件の管理 | `task_board.json`、実行概要 |
| 計画担当 | 目的と対象外・作業項目の整理 | `plan.md` |
| 設計担当 | 構造・データ・基準・失敗時の扱いの整理 | `design_note.md` |
| 実行案担当 | 実装したい作業手順の案を作る | `execution_proposal.md` |
| レビュー担当 | 抜け・矛盾・品質リスクを確認する | `review_report.md` |
| QA担当 | 確認観点・機械的検査・受入条件を整理する | `qa_checklist.md` |
| 記録担当 | 判断理由・保留事項・次回引き継ぎを残す | `decision_log.md` |
| 安全確認担当 | 禁止操作・承認待ち操作・秘密情報混入を確認する | `safety_report.md` |

## 6. 入力

| 入力 | 内容 |
|---|---|
| task request | 利用者が依頼した作業内容 |
| role catalog | 各ロールの責任・読む情報・書く成果物 |
| shared memory | プロジェクト方針・制約・既存決定 |
| approval rule | AIだけで進めてよい操作・人間確認が必要な操作・禁止操作 |
| fixture | 模擬実行で使う固定入力 |

## 7. 出力

| 出力 | 内容 |
|---|---|
| task board | タスク状態・担当・保留理由・承認待ち項目 |
| role outputs | 各ロールが作成した計画・設計・レビュー・QA・記録 |
| run log | 実行日時・利用モード・各ロールの結果・停止理由 |
| final report | 利用者向けの最終報告・残課題・次の作業 |

## 8. 処理方針

1. 利用者の依頼をタスクボードへ登録する。
2. 調整役がタスクを分解し、実行するロール・項目を決める。
3. 各ロールは、自分に必要な入力だけを読み、成果物をファイルに残す。
4. レビュー担当とQA担当が、成果物の抜け・矛盾・確認不足を指摘する。
5. 安全確認担当が、危険操作・秘密情報・承認待ち項目を確認する。
6. 指摘事項を反映し、調整役が最終報告を作る。
7. ローカルLLMが未接続の場合は、模擬応答で同じ流れを確認する。

## 9. ローカルLLM方針

- LM Studio の OpenAI互換APIを利用する。
- Dockerから呼ぶ場合は既存のStudyAI 方針に合わせ、ホストのLM Studioを参照する。
- 1つのローカルLLMを、ロールプロンプトを切り替えながら順番に呼び出す。
- 複数モデルの同時常駐や並列推論はMVP対象外とする。
- 未接続時は模擬応答を返し、教材の流れと成果物の関係を確認できるようにする。

## 10. 承認基準

| 区分 | 扱い |
|---|---|
| AIだけで可能 | 要件整理・計画案・レビュー観点・QA観点・ログ整理 |
| 人間確認が必要 | ファイル変更、コマンド実行、外部送信、依存追加、長時間実行 |
| 禁止 | 秘密情報の利用、実顧客データの利用、ファイル削除の自律実行、OS設定変更 |

教材では、人間確認が必要な操作は実行せず、承認待ちとしてタスクボードと安全確認結果に記録する。

## 11. 停止条件

- 最大ラウンド数に到達した。
- レビューまたはQAで重大な未解決事項が残った。
- 安全確認で人間確認が必要な操作が見つかった。
- ローカルLLM接続に失敗し、模擬実行へ切り替えた。
- 必要な成果物がすべて作成され、最終報告が作成された。

## 12. 確認観点

- 1つのAIに全情報を渡さない理由を説明できるか。
- ロールごとの責任と成果物を説明できるか。
- タスクボード・共有記憶・判断ログの違いを説明できるか。
- 人間確認が必要な操作をAIが勝手に実行しない仕組みになっているか。
- ローカルLLM未接続時でも模擬実行で学習できるか。

## 13. 後続工程への引き継ぎ

詳細設計では、`task_board.json`・`role_catalog.json`・`run_log.json`・各ロール成果物のテンプレート・模擬応答・確認スクリプトを具体化する。
