# web31 IssueとPRで作業を説明する

作業前にIssueで目的と完了条件を定義し、作業後にPRで変更理由、影響範囲、確認結果を説明するテーマです。

## このテーマでできるようになること

- 背景、目的、作業内容、完了条件を分けて書ける
- 今回やらないことを対象外として明示できる
- 変更内容と変更理由を分けてPRへ記録できる
- 実際に確認した結果だけをチェック済みにできる

## 資料を見る前の確認問題

- 背景と目的は何が違いますか。
- 完了条件を作業後に決めると何が起きますか。
- PRへ変更ファイル一覧だけを書くと、レビューで何が不足しますか。

## 15分で再開する

1. sample Issueとsample PRを続けて読む。
2. Issueの完了条件がPRの確認結果に対応する箇所を探す。
3. 次に行う小さな作業をIssueテンプレートへ書く。
4. 対象外を1つ、確認方法を1つ明記する。

## IssueとPRの役割

| 文書 | 時点 | 主な問い |
|---|---|---|
| Issue | 作業前 | なぜ必要か、何を達成するか、何をしないか |
| PR | 作業後 | 何を変えたか、なぜその変更か、どう確認したか |

## 作業サイクル

```text
Issueで背景・目的・完了条件を定義
  ↓
実装・文書変更
  ↓
完了条件に沿って検証
  ↓
PRへ変更・理由・影響・結果を記録
  ↓
未対応事項を次のIssue候補へ残す
```

## 演習

1. READMEのリンク切れ修正を題材に、小さなIssueを書く。
2. 修正後のPRを書き、影響範囲を画面・API・DB・文書で分類する。
3. 実行していないテストのチェックを未完了のまま残す。
4. 追加要望を対象外または未対応事項へ移し、今回の範囲を守る。

## レビュー観点

- 目的と変更内容が対応しているか
- 完了条件が検証可能な表現か
- 影響範囲に漏れがないか
- 確認結果にコマンド、URL、期待結果があるか
- 未確認事項を成功扱いにしていないか
- 対象外の変更が混ざっていないか

## 自分の言葉で説明する

- IssueとPRを1つの作業記録としてつなぐ方法を説明してください。
- 「コードを変更した」と「不具合原因を解消した」は何が違いますか。
- レビューする人が再確認できるPRには何が必要ですか。

## 記入時の注意

- 背景、目的、変更内容、変更理由を混ぜない。
- 実際に確認した内容だけをチェック済みにする。
- 秘密情報や個人情報をIssue・PRへ貼らない。
- 大きな作業は、独立して検証できる単位へ分ける。

## 学習完了の目安

- [ ] 小さな作業のIssueを1件書いた
- [ ] 完了条件に対応するPR確認結果を書いた
- [ ] 対象外と未対応事項を区別した
- [ ] 第三者が変更理由と再確認方法を理解できるか見直した
